# bep2-offline-sign

امضاکنندهٔ **آفلاین و غیررسمی** برای ابزار رسمی بازیابی BNB Beacon Chain
(<https://github.com/bnb-chain/token-recover-self-service-tools>)، برای کسانی که افزونهٔ Trust Wallet
(که ابزار انتظار دارد) در دسترسشان نیست.

[English](README.md)

> **وابسته به BNB Chain، بایننس یا Trust Wallet نیست. مسئولیت استفاده با خودتان است.**
> این ابزار با **کلید خصوصی** سروکار دارد. کد را بخوانید (حدود ۶۰ خط، بدون دسترسی شبکه و بدون
> نوشتن فایل)، روی سیستم تمیز و غیرمشترک اجرا کنید، و هیچ‌وقت کلید، seed یا امضا را در چت،
> Issue یا سایت قرار ندهید.

## چه می‌کند

مرحلهٔ ۲ ابزار رسمی یک پیام JSON می‌سازد که معمولاً افزونهٔ کیف پول آن را امضا می‌کند. این اسکریپت
**همان بایت‌ها** را آفلاین امضا می‌کند و `signature` و `publicKey` را چاپ می‌کند تا در مرحلهٔ ۳
(فیلدهای دستی ابزار) paste کنید.

* روش امضا: `secp256k1`، ECDSA روی **یک‌بار SHA-256 از دقیقاً همان رشتهٔ UTF-8 پیام**، امضای ۶۴ بایتی
  `r||s` (RFC 6979، low-S) و کلید عمومی ۳۳ بایتی فشرده، هر دو با پیشوند `0x`.
* با امضای نمونه و کلید عمومی که در README ابزار رسمی آمده تأیید شده
  (`npm run verify-vector` ← `noble: true` و `OpenSSL: true`، و آدرس `bnb1…` مشتق‌شده با نمونه می‌خواند).
* قبل از چاپ، اسکریپت (۱) آدرس `bnb1…` را از کلید مشتق می‌کند و در صورت ناهماهنگی متوقف می‌شود،
  (۲) امضا را با noble تأیید می‌کند، و (۳) مستقلاً با OpenSSL داخلی Node دوباره تأیید می‌کند
  (که پیام خام را خودش هش می‌کند و هش‌دوباره ناشی از تفاوت نسخه‌ها را می‌گیرد).

آنچه **اثبات نمی‌کند**: پذیرش درخواست توسط سرور. فقط مرحلهٔ ۳ این را نشان می‌دهد و مرحلهٔ ۳
هیچ تراکنشی ارسال نمی‌کند.

## پیش‌نیازها

* Node.js نسخهٔ ۲۴ به بالا (روی Windows PowerShell آزمایش شده)
* ابزار رسمی، **فقط** از <https://github.com/bnb-chain/token-recover-self-service-tools> کلون شود
* یک کیف پول BSC (مثلاً MetaMask) برای دریافت، با کمی BNB برای گس

## نصب

```powershell
git clone https://github.com/darangworks/bep2-offline-sign.git
cd bep2-offline-sign
npm ci --ignore-scripts
npm ls --depth=0        # انتظار: @noble/curves@1.9.7  @noble/hashes@1.8.0  @scure/base@1.2.6
npm run verify-vector   # انتظار: noble: true / OpenSSL: true
```

## بررسی خودکار با GitHub Actions

با هر `push` و `pull request`، گیت‌هاب به‌طور خودکار آزمون بازتولیدپذیری را اجرا می‌کند؛ اجرای دستی هم ممکن است. این گردش‌کار نسخه‌های قفل‌شدهٔ وابستگی‌ها را با غیرفعال‌کردن اسکریپت‌های چرخهٔ نصب نصب می‌کند، سپس `npm run verify-vector` را اجرا می‌کند تا امضای نمونهٔ منتشرشده به‌طور مستقل با **noble و OpenSSL** بررسی شود و در پایان نسخه‌های وابستگی‌های نصب‌شده را گزارش می‌دهد.

این آزمون فقط بررسی رگرسیون و بازتولیدپذیری است؛ **ممیزی امنیتی مستقل نیست** و پذیرش درخواست توسط سرویس بازیابی را ثابت نمی‌کند. گردش‌کار به کلید خصوصی شما نیاز ندارد و آن را دریافت یا استفاده نمی‌کند.

فایل گردش‌کار: [`.github/workflows/verify-vector.yml`](.github/workflows/verify-vector.yml).

## استفاده

1. ابزار رسمی را اجرا کنید؛ **مرحلهٔ ۱** (آدرس ← لیست) و **مرحلهٔ ۲** (توکن، مقدار، آدرس BSC،
   `Generate Sign Message`). «Sign with Wallet» را رد کنید.
2. پیام JSON را با Notepad در یک فایل (مثلاً `message.json`) ذخیره کنید، تک‌خطی و بدون ویرایش.
   برای همین فیلدها، پیام فشردهٔ تک‌خطی حدود ۳۳۲ بایت است.
3. فیلدها را بررسی کنید: `amount` (هگز)، `token_symbol` (هگز) و `recipient` = آدرس BSC **خودتان**.
4. امضا. بعضی ترمینال‌ها paste در پرسش مخفی را نمی‌پذیرند؛ پایپ از کلیپ‌بورد این مشکل را دور می‌زند:

   ```powershell
   Get-Clipboard | node sign-bbc.mjs bnb1ADDRESS_SHOMA message.json
   ```
   (یا `node sign-bbc.mjs bnb1ADDRESS_SHOMA message.json` و تایپ/paste در پرسش مخفی.)
   خروجی: `Message: N bytes, sha256=…` و سپس `signature` و `publicKey`.
5. کلیپ‌بورد و تاریخچهٔ آن را پاک کنید (`Win+V` ← Clear all). قبلش دو مقدار را موقتاً جایی نگه دارید.
6. چک اختیاری مقادیری که می‌خواهید paste کنید (فقط مقادیر عمومی، بدون کلید):
   `node check-pasted.mjs 0xPUBLICKEY 0xSIGNATURE message.json bnb1ADDRESS_SHOMA`
7. **مرحلهٔ ۳** ابزار: نماد، `publicKey`، `signature`، آدرس BSC ← `Get Approval`.
   موفقیت یعنی `proofs` و `approval_signature` برمی‌گردند (هنوز چیزی روی زنجیره ارسال نشده).
8. **مرحلهٔ ۴** `Generate Payload` و سپس ارسال `recover` از کیف پول BSC به قرارداد بازیابی
   (آدرس و گس را از راهنمای رسمی بگیرید)، مثلاً از تب «Write Contract» در BscScan.
   سلکتور `0xbfb5a6a1` با `recover(bytes32,uint256,bytes,bytes,bytes,bytes32[])` می‌خواند؛ ترتیب آرگومان‌ها:
   `tokenSymbol، amount، ownerPubKey، ownerSignature، approvalSignature، merkleProof`.
   فقط `recover` را بزنید؛ بقیهٔ توابع آن قرارداد مدیریتی‌اند.

## بعد از تراکنش: دورهٔ انتظار

`recover` موفق فقط مبلغ را **قفل** می‌کند (رویداد `TokenRecoverLocked` با زمان `unlockAt`، ۷ روز بعد).
دارایی فوراً نمی‌رسد. مخزن رسمی انتظار کل را حدود ۳۰ روز می‌گوید (قفل ۷ روزه + حدود ۲۳ روز پردازش؛
به PR مستندات مربوط به دورهٔ انتظار در مخزن رسمی نگاه کنید). `recover` را **دوباره نزنید**. وضعیت را
فقط‌خواندنی ببینید:

```
https://mainnet-token-recover-api.bnbchain.org/api/recover/token/bnb1ADDRESS_SHOMA?symbol=BNB
```

کاربران `status` برابر ۴ را Locked و ۶ را Unlocked گزارش کرده‌اند (از گزارش‌های Issues، نه مستندات رسمی).

## عیب‌یابی

* `Key must be 64 hex characters`: متن paste‌شده کلید خام ۶۴ هگز نیست (قالب دیگر، خط شکسته، یا
  paste در پرسش مخفی قبول نشده). از روش پایپ استفاده کنید.
* `MISMATCH: this key controls bnb1…`: کلید برای آدرس دیگری است؛ چیزی امضا نشد.
* خطای `record not found` در مرحلهٔ ۳: یک بار دیده شد و در تلاش بعدی با همان امضا موفق شد؛ علتش
  نامعلوم است. فیلدهای نماد/آدرس را بررسی کنید و اگر پیام عوض نشده دوباره امضا نکنید.
* خطای `verify signature failed`: ورودی‌های مرحلهٔ ۲ و ۳ باید یکسان باشند و پیام امضاشده بایت‌به‌بایت
  همان پیام تولیدشدهٔ ابزار.

## محدودیت‌ها

* جاوااسکریپت نمی‌تواند رشتهٔ تایپ‌شدهٔ کلید را از حافظه مطمئن پاک کند؛ بعد از کار ترمینال را ببندید.
* پرسش مخفی از یک قلاب مستندنشدهٔ readline استفاده می‌کند؛ اگر کلید روی صفحه دیده شد، متوقف شوید.
* فقط برای BNB بومی روی Windows PowerShell آزمایش شده؛ توکن‌های دیگر و سیستم‌عامل‌های دیگر آزمایش نشده.
* پشتیبانی از کیف پول سخت‌افزاری ندارد.
* ممیزی مستقل انجام نشده. [SECURITY.md](SECURITY.md) را ببینید.
